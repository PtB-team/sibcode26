## 0. Зачем это всё

**Главная задача — превентивно реагировать на финансовые трудности клиента.**

В договоре зафиксировано: к 30.06 будет фундамент. Дрон прилетел 07.07, а на участке ничего нет. Платежи пока идут вовремя, но это уже звоночек: деньги, скорее всего, кончились или ушли не туда, и просрочка появится через несколько месяцев. Банк узнаёт об этом сейчас, а не когда клиент перестанет платить, и успевает мягко отреагировать: позвонить, предложить реструктуризацию или каникулы, прилететь раньше.

Отсюда цепочка:

```
снимки → стадия и % (факт) → сравнение с графиком договора (план) → сигнал риска → мера реагирования
```

Стадия и % — это **вход**, а продукт — **сигнал отставания и рекомендованная реакция**. Ошибка модели здесь стоит дорого: ложная тревога означает лишний звонок хорошему клиенту, пропуск — потерянное время. Поэтому тревога поднимается только по уверенному результату, а неуверенный сначала уходит на пересъёмку.

В этом документе:
- **агент готовности** (раздел 3): что построено по факту;
- **раннее предупреждение** (раздел 4): план против факта, сигналы, уровни риска, меры;
- **агент материала стен** (раздел 5): вторая часть, сравнение «что построено» с проектом;
- **API** (раздел 6) и **фронт** (раздел 7);
- **критерии хакатона** (раздел 11): код, новизна, презентация.

Освоение участка и LLM-дирижёр — следующие этапы, сюда не входят. Правила раннего предупреждения из раздела 4 — это и есть первая версия дирижёра.

## 1. Что делаем

```
Оператор загружает облёт (4 фасада + низкий и высокий надир)
        │
        ▼
API сохраняет снимки (sha256, EXIF) → ставит задачу в очередь
        │
        ▼
Воркер: YOLO находит элементы стройки → агрегация по ракурсам → правила
        └─ часть 2: кропы стен → классификатор материала → голосование по фасадам
        │
        ▼
Результат: стадия, % готовности, уверенность, объяснение, рамки на фото
        │
        ▼
Раннее предупреждение: факт против графика договора + платежи → уровень риска, сигналы, рекомендованная мера
        │
        ▼
Веб-морда: лента тревог → карточка объекта → «Согласен / Исправить» → «Мера принята»
```

Главный принцип: **модель ищет элементы, а стадию и % считают правила.** Поэтому каждый вывод объясним: на фото видно, что именно нашла модель и какое правило сработало.

## 2. Стек и структура

| Слой | Хакатон | Пилот |
|---|---|---|
| Язык | Python 3.11+ | Python 3.11+ |
| API | FastAPI + Pydantic | FastAPI + Pydantic |
| БД | SQLite | PostgreSQL |
| Снимки | локальная папка | MinIO / S3 |
| Очередь | отдельный процесс-воркер, задачи в таблице БД | RQ / Celery + Redis |
| ML | Ultralytics YOLO26m-det (запасной вариант YOLO11m) | то же, экспорт в ONNX / OpenVINO |
| Фронт | React / Vue, стек фронтендера | то же |

```
repo/
├── api/            # FastAPI: роуты, схемы, CORS, мок-режим
├── worker/         # процесс инференса: берёт задачи, пишет результат
├── agents/
│   ├── readiness/  # детектор + агрегация + правила → JSON
│   ├── material/   # часть 2: кропы стен + классификатор + голосование
│   └── early_warning/  # план против факта, сигналы, уровень риска, мера
├── schemas/        # общие Pydantic-модели (контракт API и агента)
├── configs/
│   ├── classes.yaml   # классы детектора, русские названия, цвета
│   ├── stages.yaml    # веса этапов и пороги
│   ├── materials.yaml # классы материала, группы, пороги сравнения
│   └── risk.yaml      # пороги отставания, уровни риска, меры
├── mocks/          # демо-объекты и снимки для мок-режима
├── data/           # датасет и разметка (не в git)
└── weights/        # веса модели (не в git)
```

Правила работы:
- Модель загружается **один раз** при старте воркера.
- Инференс **никогда не идёт внутри HTTP-запроса**.
- Контракт данных описан один раз в `schemas/`, а API и воркер его импортируют.

## 11. Хакатон: критерии оценки

Оценивают качество кода, новизну и презентацию. Ниже — что делаем под каждый критерий.

### 11.1 Качество кода

Жюри смотрит репозиторий несколько минут, поэтому важно то, что видно сразу.

**Чек-лист:**
- [ ] `docker compose up` поднимает API, воркер и фронт одной командой, `MOCK=1` по умолчанию. **Если проект не запустился у жюри, остальное неважно.**
- [ ] README в корне: что это, гифка демо, как запустить (3 команды), схема, ссылка на этот документ.
- [ ] Type hints везде, Pydantic-схемы для всех контрактов, `mypy` без ошибок.
- [ ] `ruff` (линтер и форматтер) + pre-commit.
- [ ] GitHub Actions: линтер, mypy, тесты; бейдж в README.
- [ ] **Тесты на правила**: агрегация по ракурсам, % готовности, плановый %, сигналы, уровни риска, голосование по материалу. Они без модели, пишутся быстро. На каждый демо-объект из раздела 8 — свой тест «вход → ожидаемый уровень риска и мера».
- [ ] Все пороги и веса в `configs/*.yaml`, в коде нет магических чисел.
- [ ] Модель за интерфейсом (`Detector`, `MaterialClassifier`): правила тестируются на фейковых детекциях, модель меняется без правок логики.
- [ ] Логи в JSON, понятные коды ошибок (раздел 6.4).
- [ ] Ноутбуки обучения и отчёт о метриках в `ml/`, веса — по ссылке, не в git.
- [ ] Осмысленная история коммитов, без «fix», «fix2», «final_final».

### 11.2 Новизна

Не продаём «YOLO нашёл стены» — этим никого не удивить. Новое в другом:

1. **Сигнал раньше просрочки.** Сравнение проекта с фактом ловит трудности клиента за месяцы до того, как их покажет DPD. Банк получает окно для мягкой реакции. **Это главный тезис.**
2. **Две оси сравнения с проектом:** «когда» (график) и «что» (материал). Первая ловит финансовые трудности, вторая — нецелевое использование и переоценку залога.
3. **Объяснимость через элементы.** Модель ищет элементы, стадию считают прозрачные правила, у каждого вывода есть рамка на фото и сработавшее правило. Банку и регулятору это важнее точности.
4. **Съёмка с ролями ракурсов:** 6 снимков, маска «класс × ракурс», noisy-OR по фасадам, проверка границ участка по высокому надиру.
5. **Материал «фиксируется» до отделки:** облёт планируется в окно стадии «Стены», и материал закрепляется за объектом.
6. **Защита от ложной тревоги:** неуверенный результат или не тот участок ведут к пересъёмке, а не к звонку клиенту. Для красных сигналов обязателен человек.
7. **Замкнутый контур:** правки сотрудников становятся разметкой для дообучения, отклонённые тревоги — материалом для подстройки порогов.

### 11.3 Презентация

Строим вокруг одного клиента, а не вокруг архитектуры. 8–10 слайдов, 5–7 минут.

| # | Слайд | Содержание |
|---|---|---|
| 1 | Проблема | Банк узнаёт о трудностях клиента по просрочке, когда уже поздно. Выезд на объект дорогой и редкий |
| 2 | История клиента | «По проекту фундамент к 30.06. Дрон 07.07 — пустой участок. Платежи в срок». Снимок `top_high` с границами участка |
| 3 | Решение в одной фразе | Проект против факта с дрона → сигнал до просрочки → мера |
| 4 | **Живое демо** | загрузка облёта → оранжевая тревога → карточка «по проекту / по облёту» → «Принять меру» |
| 5 | Вторая ось: материал | `obj_demo_7`: по графику, но брус вместо газобетона → красный |
| 6 | Как это работает | одна схема: 6 ракурсов → детектор → правила → план/факт → риск |
| 7 | Почему банку можно доверять | рамки на фото, правила, человек в контуре, хеши снимков |
| 8 | Цифры | точность стадии и материала на отложенных объектах; стоимость облёта против выезда; сколько дней выигрывает банк до просрочки |
| 9 | Что дальше | освоение участка, LLM-дирижёр, интеграция с АБС |
| 10 | Команда | кто что делал |

**Обязательно:**
- [ ] Видео демо 60–90 секунд. Если на защите что-то упадёт, показываем его.
- [ ] Демо запускается в мок-режиме с заранее подготовленными объектами: на защите ничего не обучаем и не ждём.
- [ ] Цифры только реальные, с пометкой «на N объектах». Если данных мало — честно так и сказать.
- [ ] Ответы на ожидаемые вопросы: «а если зима?» (сезонная пауза), «а если сняли не тот участок?» (`top_high` + кадастр), «а если модель ошиблась?» (пересъёмка, человек, дообучение), «а персональные данные?» (контур банка, локальные модели).
