# Бэкенд стадии строительства и материала стен ИЖС

Сервис принимает фотографии дома, сохраняет оригиналы и метаданные, ставит обработку в очередь и выдаёт два результата: стадию строительства с процентом готовности и шкалой банка 0 / 50 / 100, а также материал стен. Разметкой и обучением моделей занимается ML-команда; её готовые адаптеры подключаются отдельно.

По умолчанию включён **деморежим**. В нём работают загрузка, метаданные, очередь, превью и ручная проверка. Автоматического распознавания пока нет: оба результата явно содержат `is_demo: true` и `status: model_unavailable`. Это не результат YOLO.

## Запуск

Команды выполняются из корня проекта. В текущей рабочей папке `.venv` уже подготовлена. При установке на другой машине сначала создайте окружение командой `python -m venv .venv`, используя Python 3.11 или новее.

Установка только бэкенда, без PyTorch и зависимостей обучения:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-backend.txt
```

В первом терминале запустите API:

```powershell
.\.venv\Scripts\python.exe -m uvicorn api.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале запустите обработчик:

```powershell
.\.venv\Scripts\python.exe -m worker
```

В Git Bash замените `.\.venv\Scripts\python.exe` на `./.venv/Scripts/python.exe`.

Откройте [страницу проверки API](http://127.0.0.1:8000/docs). Это встроенная страница, через которую можно загружать фотографии и получать ответы до готовности фронтенда.

## Как проверить на наших фотографиях

1. На странице `/docs` выполните `POST /api/v1/objects` с телом `{"address": "Тестовый дом"}`. Скопируйте полученный `id`.
2. Откройте `POST /api/v1/objects/{object_id}/flights`, вставьте `id` и выберите снимки из одной папки `dataset`. Для снимков с EXIF поля `views`, `meta` и `flown_at` можно оставить пустыми.
3. Отметьте `target_confirmed: true` только после проверки, что на снимках нужное здание. Для папки `12` сначала нужно разобраться с кадастровым объектом: адрес супермаркета не подтверждает нужное жилое здание.
4. Из ответа скопируйте `flight_id`. В `GET /api/v1/flights/{flight_id}` статус сначала будет `queued`, затем `processing` и `done` либо `failed`.
5. В `GET /api/v1/flights/{flight_id}/images` доступны метаданные, ссылки на оригиналы и превью. Превью появляются после обработки.
6. В деморежиме `result.status` (стадия) и `material_result.status` будут `model_unavailable`. После подключения ML-адаптеров этот же запрос будет возвращать результаты моделей.

Для стадии нужны оба снимка сверху и минимум 3 фасада с известной стороной. Снимок сверху без ручного ракурса сервис делит сам по высоте из XMP DJI (`RelativeAltitude`, порог 30 м в `configs/classes.yaml`): выше — `top_high`, ниже — `top_low`. Если высоты в файле нет, например у дрона другой марки, такой снимок остаётся надиром без роли и стадия уходит на пересъёмку.

Сторону фасада `N/E/S/W` без ручного ракурса сервис определяет по азимуту камеры из XMP DJI (`GimbalYawDegree`). Фасад смотрит на камеру, поэтому `N` — северный фасад, снятый камерой, которая смотрит на юг. Дома редко стоят ровно по сторонам света, поэтому сетка 90° подгоняется под фасадные кадры конкретного облёта: дом, повёрнутый на 45°, всё равно получает четыре разные стороны, а повторные кадры одного фасада — одну. Кадр дальше 25° от сетки (угол дома) остаётся без стороны. Без азимута сторону нужно передать в `views`, иначе результат будет с причиной `FEW_FACADES`.

Если у объекта задан `parcel_geojson` (контур участка из кадастра, вершины `[lon, lat]`), GPS всех снимков сверяется с ним: снимок дальше 30 м от границы даёт причину пересъёмки `OUT_OF_PARCEL`. Воркер также проверяет каждый снимок на размытие, пересвет и недосвет: дефект даёт `BAD_IMAGE`, а у снимка появляются `quality_ok` и `quality_issues`. Попал ли дом в кадр, эта проверка не определяет.

Если статус остаётся `queued`, проверьте, что второй терминал с воркером запущен из того же каталога и использует тот же `STORAGE_DIR`.

## Что входит в первую версию

- Объекты: создание, список, карточка, необязательный проектный материал и примечания.
- Пакеты снимков: JPG/PNG, включая JPEG/MPO с дрона, 1–20 файлов, до 30 МБ каждый; дубликаты внутри пакета отклоняются. Для многокадрового контейнера обрабатывается основной кадр, оригинал сохраняется целиком.
- Сохранение оригиналов, SHA-256, EXIF, GPS, времени съёмки и наклона камеры.
- Очередь в SQLite и отдельный воркер; очередь переживает перезапуск API. После аварии воркера задание повторно доступно через 15 минут, после трёх прерываний помечается ошибкой.
- Превью и, при наличии рамок от модели, вырезанные участки стен.
- Общий результат по дому с отдельными состояниями: материал определён, скрыт отделкой, стен нет, мало данных, противоречие, нужна проверка.
- Сравнение с проектным материалом при достаточных доказательствах.
- Ручная проверка материала с сохранением автора и комментария. Ответ модели остаётся неизменным.
- Стадия строительства (раздел 3 [BACKEND.md](material/BACKEND.md)): маска «класс × ракурс», noisy-OR по независимым ракурсам (повторный снимок одного фасада не добавляет уверенности), доля окон, подразумеваемые ранние этапы, стадия, % готовности, шкала банка, уверенность, причины пересъёмки и объяснение по шаблону без LLM.
- Детекции на каждом снимке с отметкой, попали ли они в расчёт.
- Ручная проверка стадии; ответ модели остаётся неизменным. Состояние данных объекта `data_status`.
- Автоматическая роль снимка: надир по высоте, сторона фасада по азимуту. Проверка участка по кадастровому контуру и техническая проверка качества снимка.

Остальные части общей архитектуры — анализ участка, раннее предупреждение, риск и GigaChat-дирижёр — описаны в [плане команды](<material/README (2).md>) и пока не реализованы этим сервисом.

## Ручная проверка

`POST /api/v1/flights/{flight_id}/material/review` принимает результат готовой модели через `{"action": "accept"}` либо сохраняет исправление сотрудника:

```json
{
  "action": "correct",
  "material": "aerated_concrete",
  "comment": "Материал подтверждён сотрудником по снимкам и документам"
}
```

Автор передаётся заголовком `X-User`. В карточке объекта `material.reviewed: true` обозначает ручное подтверждение, а `last_flight.material_result` по-прежнему содержит исходный ответ модели. Демонстрационный ответ принять как распознанный материал нельзя; ручное исправление остаётся отдельным источником.

Стадию проверяет `POST /api/v1/flights/{flight_id}/review`: `{"action": "accept"}` либо исправление:

```json
{
  "action": "correct",
  "stage": "walls",
  "readiness_pct": 40,
  "comment": "Стропила не установлены, на снимке N штабель досок"
}
```

`bank_readiness` в исправлении можно не указывать: для `none` это 0, для `done` — 100, для остальных стадий — 50. Если окна и дверь уже стоят, передайте 100 явно. Последняя правка лежит в `readiness_review` облёта, исходный `result` не меняется.

## Файлы и настройки

| Где | Для чего |
| --- | --- |
| `api/main.py` | Приём запросов, загрузка и выдача файлов |
| `api/database.py` | Объекты, очередь, результаты, история ручных проверок |
| `api/images.py` | Проверка снимков, метаданные, превью и кропы |
| `worker/service.py` | Обработка заданий вне HTTP-запроса |
| `schemas/material.py` | Единый формат данных для бэкенда и ML-команды |
| `agents/material/model.py` | Интерфейс подключения готовой модели |
| `agents/material/aggregation.py` | Объединение результатов разных ракурсов |
| `schemas/readiness.py` | Формат детекций, результата стадии и ручной проверки |
| `agents/readiness/model.py` | Интерфейс подключения детектора стройки |
| `agents/readiness/aggregation.py` | Правила: стадия, %, шкала банка, пересъёмка |
| `agents/readiness/views.py` | Роль снимка: надир по высоте, сторона фасада по азимуту |
| `agents/readiness/parcel.py` | Попадает ли GPS снимков в участок с буфером |
| `agents/readiness/quality.py` | Размытие, пересвет и недосвет снимка |
| `configs/classes.yaml`, `configs/stages.yaml` | Классы и маска ракурсов, веса этапов и пороги |

`STORAGE_DIR` по умолчанию равен `.local/material-backend`: там находятся SQLite и загруженные копии снимков. Каталог `dataset` сервис не изменяет. `MOCK=1` включает деморежим. При `MOCK=0` обязательны обе фабрики: `MATERIAL_MODEL_FACTORY` и `DETECTOR_FACTORY` (формат `module:factory`), без любой из них воркер не стартует. `CORS_ORIGINS` задаёт адреса фронтенда через запятую. Если EXIF не содержит часового пояса, используется `PHOTO_UTC_OFFSET_HOURS=7`; это настройка, а не подтверждённый камерой часовой пояс.

До подключения готовой модели посмотрите [простое объяснение для защиты и договорённости с ML](material/HOW_IT_WORKS.md).

Детектор стройки реализует `Detector` из `agents/readiness/model.py`: `detect(image, image_id)` получает RGB-изображение Pillow с учтённым поворотом EXIF и возвращает список `Detection` с полями `image_id`, `class` (id из `configs/classes.yaml`), `conf` от 0 до 1 и `bbox` `[x1, y1, x2, y2]` в долях изображения. Детектор вызывается на всех снимках, включая верхние; какие классы с какого ракурса учитывать, решает бэкенд.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check api agents schemas worker tests
```

Тесты запускаются из `tests/`. Существующий `test.py` проверяет GPU и относится к подготовке обучения; для запуска бэкенда GPU не требуется.
