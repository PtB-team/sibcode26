# API материала стен в общей сборке · 0.5

Этот документ описывает материальную часть общей сборки. Запуск всех компонентов и изменения 0.3 — в [INTEGRATION.md](INTEGRATION.md). [API.md](API.md) содержит также план всей банковской системы. Базовый путь — `/api/v1`, схемы запросов — в `/docs` и `/openapi.json`.

Связка детектора и классификатора, дополнительные поля стены (`cls`, `bbox`, `material_conf`), параметр области `meta[].target_bbox` и ограничения автоматического выбора участка описаны в [YOLO_INTEGRATION.md](YOLO_INTEGRATION.md). У новых наблюдений `conf` относится к детектору, а `material_conf` и `confidence` — к материалу. Совместимое `class` сохраняет прежнее значение материала.

## Подключение

Начните с `GET /meta`. Ответ содержит `scope: "inspection"` и `capabilities`:

```json
{
  "wall_material": true,
  "material_review": true,
  "target_region_filter": true,
  "automatic_target_identification": false,
  "readiness": true,
  "readiness_review": true,
  "risk": false,
  "conductor": false,
  "gigachat_analysis": true,
  "alerts": false,
  "tasks": false,
  "history": true,
  "actions": true,
  "land": false,
  "valuation": true,
  "act": false,
  "registry_import": false
}
```

При этом `scope` интерфейс показывает объекты, фотографии, материалы и готовность. Справочники `risk_levels` и `steps` не обязательны для подключения модуля; они пока не возвращаются. Не запрашивайте неподдерживаемые функции при открытии приложения или карточки.

В `/meta` есть `materials`, включая отображаемые значения `hidden` и `unclear`, `views`, `material_statuses`, `mock` и `material_model_version`. Список `material_statuses` содержит пары `id/label` для всех состояний результата. Выбрать как проектный или исправленный материал можно только конкретный материал: семь значений от `brick` до `monolith` по схеме `WallMaterial`.

## Создание и чтение объекта

`POST /objects` требует только непустой `address`. Он также принимает и сохраняет поля формы фронта:

| Поля | Формат |
| --- | --- |
| `cadastral`, `loan_id`, `notes` | Строки; `cadastral` и `loan_id` могут быть `null` |
| `started_at`, `planned_completion_at`, `actual_completion_at` | `YYYY-MM-DD` или `null` |
| `overdue`, `registered`, `pledged`, `has_aerial_photo` | Логические значения, по умолчанию `false` |
| `project` | `wall_material`, `floors` ≥ 1, `footprint_m2` > 0, `source`; все поля необязательны |
| `checkpoints` | Массив `{ "stage": "walls", "due": "2027-01-01" }`, по умолчанию пустой |
| `loan` | Необязательные `amount` ≥ 0, `dpd` ≥ 0, `collateral_value_rub` ≥ 0 и массив `tranches` |
| `loan.tranches[]` | `n` ≥ 1, `amount` ≥ 0, необязательные `paid_at` (дата) и `condition_stage` |

Коды стадий для контрольных точек и условий траншей: `none`, `foundation`, `walls`, `roof`, `openings`, `facade`, `done`. Неизвестные поля запрещены, в том числе внутри вложенных объектов. Неверные даты, отрицательные суммы и контрольные точки вне указанного срока отклоняются с HTTP 400.

Кредит, сроки, признаки реестра и контрольные точки сохраняются как входные данные. Расчёт готовности, графика и риска по ним ещё не выполняется. `parcel_geojson` (замкнутый GeoJSON Polygon) и `vri` принимаются; граница участка используется при проверке положения полёта, `vri` сохраняется без правового анализа.

`GET /objects?page=1&page_size=20` возвращает `items`, `total`, `page`, `page_size`. Каждый элемент списка и ответ `GET /objects/{id}` содержат одинаковые данные объекта, в том числе:

- `last_flight_id`: идентификатор последнего загруженного облёта или `null`;
- `last_flight_at`: дата съёмки этого облёта или `null`, если её нет; дата загрузки доступна в `last_flight.uploaded_at`;
- `last_flight`: полный ответ облёта или `null`;
- `material_status`: состояние материала последнего облёта или `null` до результата;
- `data_status`: общее состояние двух модулей; `material_data_status` и `readiness_data_status` — состояния каждого отдельно;
- `material`: закреплённый материал или `null`.

Последний облёт выбирается по времени загрузки. При равных временах используется порядок добавления. Если новый облёт ещё обрабатывается, ранее закреплённый материал остаётся доступен.

## Загрузка и результат

`POST /objects/{id}/flights` принимает multipart-поля `files`, `views`, `meta`, `flown_at`, `target_confirmed`. Подробные ограничения — в `/docs` и [README](../README.md).

`target_confirmed` по умолчанию равен `false`. Передавайте `true` после того, как сотрудник проверит, что фотографии относятся к нужному зданию. Это подтверждение не заменяется координатами камеры. Без него модель может дать предположение, но автоматического закрепления не произойдёт.

После ответа HTTP 202 опрашивайте `GET /flights/{id}` до `done` или `failed`. Обработка материала находится в `material_result`; `result` содержит готовность после обработки, `land_result` пока равен `null`. Статус `done` означает завершение задания, а состояние материала нужно читать отдельно.

В `material_result.per_view[]` возвращаются оба варианта имён:

```json
{
  "image_id": "img_example",
  "view": "N",
  "visibility": "visible",
  "material": "timber",
  "confidence": 0.92,
  "class": "timber",
  "conf": 0.92,
  "crop_bbox": [0.1, 0.1, 0.9, 0.9]
}
```

`class/conf` обеспечивают совместимость с общим контрактом фронта. `material/confidence` сохраняются для существующих клиентов. Внутренний контракт ML по-прежнему использует `material/confidence`. Для скрытой стены `class = "hidden"`, для отсутствующих или неясных стен — `"unclear"`; точная причина находится в `visibility`. Готовый кроп загружайте по полному `crop_url`, включая параметр `revision`.

Показывайте последний `material_result` и при `object.material = null`: отсутствие закрепления не означает отсутствие предположения модели. Состояния `model_unavailable`, `needs_review`, `mixed`, `hidden`, `no_walls` и `insufficient_data` описаны в [HOW_IT_WORKS.md](HOW_IT_WORKS.md).

После закрепления `object.material` содержит `observed`, `confidence`, `project`, `match`, `fixed_at_flight_id`, `reviewed`. `project` совпадает с `object.project.wall_material`, если он задан. `match` сравнивает именно закреплённый материал с проектом; он может отличаться от сравнения в последнем облёте после ручного исправления. Для ручной оценки `confidence` может быть `null`: это отсутствие числовой оценки, а не 0% уверенности.

`material_data_status` для материальной части:

| Значение | Условие |
| --- | --- |
| `no_data` | Нет облётов либо нет результата распознавания, в том числе при недоступной модели |
| `processing` | Последний облёт в очереди или обрабатывается |
| `ok` | Материал определён или результат последнего облёта проверен сотрудником |
| `reshoot` | В результате выставлено `needs_reshoot` |
| `review` | Задание завершилось ошибкой либо материал требует проверки и пересъёмка явно не запрошена |

Это состояние обработки материала, а не оценка готовности дома или банковского риска.

## Ручная проверка и галерея

Используйте `POST /flights/{id}/material/review` с заголовком `X-User`:

- Принять конкретный результат настоящей модели: `{ "action": "accept" }`.
- Исправить материал: `{ "action": "correct", "material": "brick", "comment": "Причина исправления" }`.

Обработка облёта должна быть завершена. Деморезультат принять нельзя; ручное исправление возможно. Исправление записывается в `material_review` и обновляет закреплённый материал. Исходный `material_result` сохраняется. `/flights/{id}/review` проверяет готовность и возвращается в `readiness_review`/`review`. `/objects/{id}/steps` относится к будущему дирижёру и пока не реализован.

`GET /flights/{id}/images` возвращает все снимки. `view` может быть `null`, несколько файлов могут иметь одинаковый ракурс. Отображайте каждый файл; неизвестные ракурсы можно подписывать «Ракурс не указан». Стороны света автоматически не устанавливаются. Для автоматического закрепления требуются как минимум два разных подтверждённых фасада, достаточная уверенность и подтверждённое целевое здание.

## Что пока не поддерживается

`/alerts`, `/tasks`, `/objects/import`, риск, дирижёр, анализ участка и оценка стоимости остаются планом. Готовность, её ручная проверка, `/objects/{id}/history` и журнал `/objects/{id}/actions` уже работают. Эти маршруты не заменены пустыми успешными ответами. Фронтенду требуется учитывать `scope` и `capabilities` перед их вызовом.
