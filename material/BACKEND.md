## 3. ML: агент готовности

### 3.1 Вход

Один облёт объекта = **6 снимков**: 4 фасада и 2 снимка сверху.

| Ракурс | `view` | Съёмка | Что даёт |
|---|---|---|---|
| Север / Восток / Юг / Запад | `N` `E` `S` `W` | сбоку, наклон камеры ~30–45° | стены, проёмы, окна, двери, отделка |
| Низкий надир | `top_low` | сверху, низко, в кадре дом крупно | кровля / стропила, верх стен, фундамент, котлован под дом |
| Высокий надир | `top_high` | сверху, высоко, в кадре весь участок | участок целиком: есть ли вообще стройка, где она, проверка границ участка, освоение участка (раздел 14) |

Ракурс определяется из EXIF: наклон гимбала отделяет фасады от надиров, азимут даёт сторону света, высота полёта отделяет `top_low` от `top_high`. Если не получилось, ракурс передаёт фронт при загрузке.

**Снимки без EXIF.** По ответу банка данные приходят в двух комплектациях: EXIF и GPS или только GPS. Без EXIF:
- ракурс всегда передаёт фронт (поле `views`);
- GPS берётся из поля `meta` при загрузке (раздел 6.3);
- `top_high` нельзя спроецировать на землю (нет высоты, фокусного, азимута). Проверка «тот ли участок» упрощается до «GPS снимков лежит в границах участка с буфером» (раздел 4.4), а освоение участка (раздел 14) получает `status: unverified`.

**Какие классы с какого ракурса учитываются.** Детектор запускается на всех 6 снимках, но в агрегацию попадают только осмысленные пары, остальное отбрасывается как шум:

| Класс | Фасады | `top_low` | `top_high` |
|---|---|---|---|
| `site_prep`, `foundation` | ✓ | ✓ | ✓ |
| `walls_partial`, `walls_full` | ✓ | ✓ (верх стен без кровли) | — |
| `roof_frame`, `roof_covered` | ✓ | ✓ **основной** | — |
| `opening_empty`, `window_installed`, `door_installed`, `facade_finish` | ✓ **только** | — | — |
| `building`, `outbuilding`, `fence`, `paving` | — | — | ✓ **только** (раздел 14) |

Маска задаётся в `configs/classes.yaml`.

**Зачем `top_high`:**
- **Проверка, что сняли нужный участок.** По высоте и GPS снимка его углы проецируются на землю и сравниваются с границами из кадастра. Это основа защиты от ложной тревоги (раздел 4.4).
- **Доказательство `NOTHING_BUILT`.** Пустой участок целиком на одном кадре — главная картинка для сотрудника и для суда.
- **Освоение участка** (раздел 14): посадка дома по кадастру, отступы от границ, доп. постройки, забор.

**Обучение.** `top_high` снимается с большой высоты, поэтому дом на нём мелкий. Для стадии по нему достаточно классов `site_prep` и `foundation` и детекции «есть стройка / нет», а всё остальное берётся из `top_low` и фасадов. На этом снимке обязательно `imgsz=1280` или нарезка на тайлы.

### 3.2 Классы детектора

| id | Класс | Подпись в UI | Что это |
|---|---|---|---|
| 0 | `site_prep` | Подготовка участка | котлован, разметка, траншеи |
| 1 | `foundation` | Фундамент | лента, плита, сваи с ростверком |
| 2 | `walls_partial` | Стены в процессе | стены не до проектной высоты |
| 3 | `walls_full` | Стены выведены | коробка стен завершена |
| 4 | `roof_frame` | Стропила | стропильная система без покрытия |
| 5 | `roof_covered` | Кровля | кровля покрыта |
| 6 | `opening_empty` | Пустой проём | проём окна или двери без заполнения |
| 7 | `window_installed` | Окно | окно установлено |
| 8 | `door_installed` | Входная дверь | дверь установлена |
| 9 | `facade_finish` | Отделка фасада | сайдинг, штукатурка, облицовка |
| 10 | `building` | Дом сверху | основное строение на `top_high`: стены или кровля, вид сверху |
| 11 | `outbuilding` | Хозпостройка | баня, гараж, сарай |
| 12 | `fence` | Забор | ограждение участка |
| 13 | `paving` | Дорожки и площадки | мощение, отсыпка, парковка |

Классы 10–13 размечаются только на `top_high` и нужны для раздела 14. Источник правды — `configs/classes.yaml`. Фронт получает список через `GET /meta`.

### 3.3 Агрегация по ракурсам

1. По каждому классу берётся максимальная уверенность на каждом снимке, **с учётом маски ракурсов** (раздел 3.1): окно на снимке сверху не считается.
2. Снимки объединяются по noisy-OR: `P = 1 − Π(1 − conf_i)`. Элемент, найденный на трёх фасадах, надёжнее, чем на одном.
3. Доля окон: `windows_ratio = window_installed / (window_installed + opening_empty)` по всем фасадам.
4. Иерархия: более поздний этап подразумевает ранние. Есть кровля — значит, есть стены и фундамент, даже если их не видно. Такие элементы помечаются `implied: true`.

### 3.4 Правила: стадия и %

| Стадия | `stage` | Условие | Вклад в % |
|---|---|---|---|
| Нет работ | `none` | ничего не найдено (`site_prep` даёт 0–5%) | 0 |
| Фундамент | `foundation` | `foundation` | 15 |
| Стены | `walls` | `walls_partial` даёт ½, `walls_full` — полный вклад | 30 |
| Кровля | `roof` | `roof_frame` даёт ½, `roof_covered` — полный вклад | 20 |
| Окна и двери | `openings` | `windows_ratio` × 10 + дверь 5 | 15 |
| Фасад | `facade` | доля фасадов с `facade_finish` | 10 |
| Готов | `done` | всё выше, `windows_ratio ≥ 0.9`, дверь есть | 10 |

- **Стадия** — последний начатый этап.
- **%** — сумма вкладов с учётом частичных этапов.
- «Готов» означает «**внешне** завершён»: внутреннюю отделку и коммуникации с дрона не видно. Так и пишем в отчёте.

**Шкала банка.** Банк оценивает готовность тремя уровнями: 0% — ничего нет; 50% — условно фундамент, стены, возможно каркас крыши; 100% — готовый объект со стенами, крышей, вставленными окнами и дверями. Наружу (карточка, акт, дирижёр) отдаём шкалу банка `bank_readiness`, а свои 7 стадий и веса оставляем внутри: без них не посчитать отставание (раздел 4) и прогноз (раздел 4.8).

| `bank_readiness` | Наши стадии и условия |
|---|---|
| 0 | `none` |
| 50 | от `foundation` до `openings`, пока не выполнено условие для 100 |
| 100 | `roof_covered` есть, `windows_ratio ≥ 0.9`, дверь есть; отделка фасада не требуется |

Для дирижёра «ОН построен» = `bank_readiness = 100` или фактическая дата завершения в реестре. Веса этапов — наша внутренняя шкала, хранятся в `configs/stages.yaml`.

### 3.5 Уверенность и пересъёмка

`confidence` стадии = min(уверенность элементов текущей стадии, уверенность в том, что элементов следующей стадии нет).

`needs_reshoot = true`, если:

| Код | Причина |
|---|---|
| `NO_TOP_LOW` | нет низкого надира: не видно кровлю |
| `NO_TOP_HIGH` | нет высокого надира: нельзя проверить участок, тревога `NOTHING_BUILT` невозможна |
| `FEW_FACADES` | меньше 3 фасадов |
| `OUT_OF_PARCEL` | снимки сделаны не над участком из кадастра |
| `LOW_CONFIDENCE` | `confidence` ниже порога (по умолчанию 0.6) |
| `VIEWS_CONFLICT` | ракурсы противоречат друг другу (на `top_low` кровля, на фасадах только стропила) |
| `BAD_IMAGE` | снимок размыт, пересвечен или дом не в кадре |

```json
{

  "rules": "stages@v1",
  "stage": "roof",
  "stage_label": "Кровля",
  "readiness_pct": 55,
  "bank_readiness": 50,
  "confidence": 0.78,
  "elements": {
    "foundation":   {"present": true,  "implied": true},
    "walls_full":   {"present": true,  "conf": 0.93, "views": ["N", "E", "S"]},
    "roof_frame":   {"present": true,  "conf": 0.81, "views": ["top_low", "N"]},
    "roof_covered": {"present": false, "conf": 0.12}
  },
  "windows_ratio": 0.0,
  "explanation": "Стены выведены (3 фасада), стропила установлены, кровельного покрытия нет",
  "needs_reshoot": false,
  "reshoot_reasons": []
}
```

`explanation` собирается шаблоном из сработавших правил, **без LLM**.

### 3.7 Обучение и метрики

- Разметка: 300–500 снимков, классы 0–9, по 30–50 объектов на каждую стадию. Классы 10–13 — отдельно, только на `top_high`. Инструмент — CVAT или Roboflow.
- Train/val делим **по объектам, а не по снимкам**: снимки одного дома не должны попадать в обе выборки.
- `imgsz=1280`, иначе мелкие элементы теряются.
- Метрики:
  - mAP50 детектора — для ML;
  - **точность стадии**, **точность `bank_readiness`** и **MAE по %** на отложенных объектах — для банка и для демо.

## 4. Раннее предупреждение: план против факта

Работает после каждого облёта и раз в день по расписанию: даже если дрон не прилетел, просроченный срок без подтверждения — уже сигнал.

Суть простая: **в договоре и проектной документации написано, что должно быть, дрон показывает, что есть на деле, а система сравнивает.** Результат уходит дирижёру (раздел 13): сигнал риска запускает ветки схемы банка раньше, чем их запустил бы один только срок.

Сравнение идёт по двум осям:

| Ось | «Должно быть» | «На деле» (дрон) | Когда |
|---|---|---|---|
| **Когда** | срок строительства из реестра; график стадий, если есть | стадия и % на дату облёта | **MVP**, этот раздел |
| **Что** | материал стен по проекту, если он есть | материал по фасадам | **часть 2**, раздел 5 |
| **Где** | границы участка и ВРИ из кадастра | посадка дома и отступы по `top_high` | раздел 14 |

Расхождение по «когда» — ранний признак финансовых трудностей. Расхождение по «что» — признак нецелевого использования или строительства не по проекту.

### 4.1 Входные данные

Минимальный набор — то, что есть в реестре банка (`Реестр_для_теста.xlsx`). Всё остальное необязательно: если поля нет, зависящие от него сигналы не считаются.

| Что | Откуда | Хакатон |
|---|---|---|
| Срок: дата начала строительства, плановая дата завершения | реестр | импорт `POST /objects/import` |
| Фактическая дата завершения, ОН зарегистрирован, залог оформлен | реестр | импорт |
| ПЗ (просроченная задолженность): да / нет | реестр, позже АБС | импорт; DPD в днях — необязательно |
| Есть ли фото с неба | реестр | импорт |
| Факт: стадия, %, `bank_readiness`, дата облёта, уверенность | агент готовности (раздел 3) или правка человека | реальный |
| График стадий: контрольные точки «стадия к дате» | проектная документация | необязательно, в реестре нет |
| Транши | АБС | необязательно, в реестре нет |
| Проект: материал стен, этажность, площадь | проектная документация | необязательно, в реестре нет |
| Границы участка, ВРИ | кадастровые сведения по номеру | заранее выгруженные контуры в `mocks/parcels/` или ручной ввод |

Правка человека всегда приоритетнее вывода модели.

### 4.2 Плановый % на дату

Если график стадий есть, каждая контрольная точка переводится в % по весам из `stages.yaml` (фундамент = 15, стены = 45, кровля = 65 …), между точками план интерполируется линейно, до первой точки отсчёт идёт от даты начала строительства (0%).

Если графика нет (как в реестре), план линейный: 0% на дату начала, 100% на плановую дату завершения.

```
plan_pct(t)     — сколько должно быть готово к дате t
fact_pct        — сколько готово по последнему облёту
lag_pct         = plan_pct(дата облёта) − fact_pct
lag_days        = дата облёта − дата, когда по плану должно было быть fact_pct
term_left_pct   = (плановая дата − сегодня) / (плановая дата − дата начала); < 0 — срок истёк
```

`lag_days` понятнее людям: «отстаёт на 45 дней» говорит больше, чем «на 12%». `term_left_pct` — то, по чему ветвится схема банка (раздел 13).

### 4.3 Сигналы

| Код | Сигнал | Условие (пороги в `risk.yaml`) | Вес |
|---|---|---|---|
| `CHECKPOINT_MISSED` | Контрольная точка сорвана | срок стадии прошёл, по облёту стадия не достигнута; только при графике стадий | высокий |
| `DEADLINE_PASSED` | Срок строительства истёк | плановая дата прошла, `bank_readiness < 100` | высокий |
| `NOTHING_BUILT` | На участке ничего нет | `stage = none` после первой контрольной точки, а без графика — после доли срока `nothing_built_after` (заглушка 25%) | критический |
| `LAG` | Отставание от плана | `lag_days ≥ 30` (жёлтый), `≥ 60` (оранжевый) | средний/высокий |
| `FORECAST_LATE` | Не успевает к сроку | прогноз завершения позже плановой даты (раздел 4.8) | средний |
| `STALLED` | Стройка стоит | прирост < 3% за ≥ 45 дней между облётами (кроме сезонной паузы) | высокий |
| `REGRESS` | Откат | % упал между облётами (разобрали, сгорело или ошибка модели → проверка) | высокий |
| `CHECKPOINT_UNVERIFIED` | Нет подтверждения | срок точки прошёл, облёта после него нет | низкий → облёт |
| `OVERDUE` | Просроченная задолженность | ПЗ = да в реестре или DPD > 0 | по сроку |
| `MISUSE_SUSPECT` | Подозрение на нецелевое использование | транш выдан, а за ≥ 60 дней после него прироста нет; только при данных о траншах | высокий |
| `MATERIAL_MISMATCH` | Материал не по проекту | часть 2, раздел 5.5; только при проектном материале | высокий |
| `MATERIAL_DEVIATION` | Материал отличается в пределах группы | часть 2, раздел 5.5 | низкий |
| `MATERIAL_UNVERIFIED` | Материал не подтверждён | стадия «Стены» пройдена, а материал так и не увидели | низкий |

**Сезонная пауза.** С декабря по февраль `STALLED` и `LAG` смягчаются на один уровень: зимняя остановка в Сибири — норма. Месяцы паузы задаются в конфиге.

Сигналы освоения участка (`OUT_OF_BOUNDS`, `SETBACK_SUSPECT`, `VRI_MISMATCH`) и переоценки (`REVALUATION_NEEDED`) в уровень риска не входят: это вопрос к документам и залогу, а не к платёжеспособности. Они описаны в разделах 14 и 15.

### 4.4 Защита от ложной тревоги

Тревогу по фото поднимаем, только если факту можно верить:

1. `confidence` агента ≥ 0.7 **или** результат подтверждён человеком.
2. Сняли именно этот участок:
   - есть EXIF: проекция `top_high` на землю пересекается с границами участка из кадастра, а GPS фасадов лежит рядом с участком;
   - только GPS: точки GPS всех снимков лежат в границах участка с буфером (`parcel_buffer_m`, заглушка 30 м).

   Иначе это не «ничего нет», а «сняли не тот участок» (`OUT_OF_PARCEL` → пересъёмка).
3. Для `NOTHING_BUILT` и `REGRESS` нужно подтверждение человеком **до** перехода в красный.

Если условия не выполнены, вместо тревоги ставится задача «повторный облёт» с приоритетом.

### 4.5 Уровень риска и что делает дирижёр

Уровень = максимум по сигналам с учётом их сочетания. Главная идея: **стройка отстаёт, а платежи ещё идут** — это и есть окно для превентивной работы. Сами меры — шаги и стратегии из схемы банка (раздел 13); уровень риска решает, **насколько раньше** схема запускается.

| Уровень | Типичная ситуация | Что делает дирижёр | Тип |
|---|---|---|---|
| 🟢 `green` | по плану, ПЗ нет | схема банка без изменений: напоминания по сроку, облёты по расписанию | авто |
| 🟡 `yellow` | `LAG` до 60 дней, `FORECAST_LATE` или `CHECKPOINT_UNVERIFIED`, ПЗ нет | внеплановый облёт (`FLIGHT_TASK`, Стратегия 1) в ближайшие 14 дней | авто |
| 🟠 `orange` | `CHECKPOINT_MISSED` / `DEADLINE_PASSED` / `STALLED` / `LAG ≥ 60`, ПЗ нет | **сразу вход 3: звонок клиенту, узнать причину** — не дожидаясь последних 30% срока | шаг для сотрудника |
| 🔴 `red` | `NOTHING_BUILT`, `MISUSE_SUSPECT`, `MATERIAL_MISMATCH`, или стройка стоит **и** ПЗ есть | ручная проверка (`MANUAL_INSPECTION`), затем дальше по схеме банка | после подтверждения |

Мягкие шаги (облёт, напоминание) выполняются автоматически. Всё, что затрагивает деньги клиента или его права (реструктуризация, доп. финансирование, замена обеспечения, суд, реализация), идёт только после подтверждения сотрудником.

Каждый шаг и решение записываются в журнал: кто, когда, что сделал, с каким результатом. По этому журналу потом измеряется эффект: сколько оранжевых объектов не дошли до ПЗ.

### 4.6 Расписание облётов

Основа — правила схемы банка по сроку (раздел 13.3, вход 1):

| Где объект по сроку | По схеме банка | Мы добавляем |
|---|---|---|
| осталось > 70% срока | SMS/PUSH: напоминание о плановой дате | — |
| осталось 30–70% | в схеме ветки нет (вопрос 12.1) | **контрольный облёт при пересечении 50% срока**: по линейному плану к этому моменту должна быть половина, это уровень 50 по шкале банка |
| осталось ≤ 30% | полётное задание, SMS об осмотре, Стратегия 1 | — |
| срок истёк | полётное задание, SMS об осмотре, Стратегия 1 | — |

Дополнительно:
- если есть график стадий — облёт через 7 дней после каждого срока стадии;
- облёт в окне стадии «Стены», пока кладка не закрыта отделкой: только в этот момент можно увидеть материал (раздел 5.3);
- при `yellow` и выше следующий облёт сдвигается на ближайшие 14 дней.

**Когда летать нельзя.** Ответ банка: ждать. Окно полётов (месяцы, погода) задаётся в конфиге; задание, которое попало вне окна, ждёт ближайшего окна и показывается в карточке как «облёт отложен».

### 4.7 Выход

```json
  "evaluated_at": "2026-10-28T12:00:00+07:00",
  "risk_level": "orange",

  "next_checkpoint": null,

  "dpd": null,
  "signals": [
    {
      "code": "LAG",

      "severity": "high",
      "text": "Строительство с 27.10.2025 по 31.10.2027. К 28.10.2026 по плану 50%, облёт: фундамент, 15%. Отставание 256 дней",
```

`next_checkpoint` равен `null`, если графика стадий нет.

### 4.8 Прогноз завершения

Нужен схеме банка (ветка 5: «AI-прогноз завершения строительства в срок») и сигналу `FORECAST_LATE`. Считается правилом, без ML:

```
скорость     = (fact_pct − fact_pct_опорный) / строительные_дни(опорная дата → дата облёта)
опорная точка = предыдущий облёт, если он был ≥ 30 дней назад; иначе дата начала и 0%
прогноз      = дата облёта + (100 − fact_pct) / скорость   (дни считаются только в строительный сезон)
on_time      = прогноз ≤ плановая дата + допуск (заглушка 30 дней)
скорость ≤ 0 → «не построит» (completion_at = null, on_time = false)
```

- Строительный сезон (месяцы) — в конфиге, зимние месяцы в скорость не входят.
- `basis`: `flights` — по двум облётам, `from_start` — по одному облёту от даты начала. При `from_start` прогноз грубый, и в карточке это видно.
- Если факт поправил человек, прогноз считается по правке.

## 5. Часть 2: агент материала стен

Работающий контур нашего модуля описан в [README сервиса](../README.md), простое объяснение для защиты и контракт с ML — в [HOW_IT_WORKS.md](HOW_IT_WORKS.md). Разметкой и обучением занимается ML-команда. Наш бэкенд отвечает за приём снимков, метаданные, очередь, подключение готовой модели, объединение её наблюдений и ручную проверку. До передачи модели включён явный деморежим без автоматического распознавания.

Первая часть отвечает на вопрос «**когда**»: успевает ли стройка по графику. Вторая — на вопрос «**что**»: из чего строят.

Материал нужен для двух вещей:
- **оценка стоимости и переоценка залога** (раздел 15) и **акт осмотра** (раздел 16): работает всегда;
- **сравнение с проектом**: в проекте газобетон, а по факту брус — значит, дом подешевле, а разница в деньгах ушла куда-то ещё. Это признак нецелевого использования. Работает, только если проектный материал известен: в реестре его нет (вопрос 12.4).

### 5.1 Каскад моделей

```
4 фасада ──► [det] агент готовности (уже работает, раздел 3)
                 │  рамки walls_partial / walls_full
                 ▼
             вырезать стену (+10% поля), отбросить мелкие и перекрытые кропы
                 │
                 ▼
             [cls] YOLO26m-cls: материал на каждом кропе
                 │
                 ▼
             голосование по фасадам → материал объекта
                 │
                 ├──► оценка стоимости (раздел 15), акт осмотра (раздел 16)
                 ▼
             сравнение с project.wall_material, если он есть → сигнал MATERIAL_MISMATCH
```

Это каскад: классификатор видит **только кроп стены** из детектора, без неба, соседей и техники. Поэтому он учится на небольшом датасете, а точность выше, чем при классификации целого кадра. Детектор новый не нужен — переиспользуется детектор из части 1.

Снимки сверху в материал не идут: с них материал стен не виден.

### 5.2 Классы материала

| id | Класс | Подпись в UI | Группа |
|---|---|---|---|
| 0 | `brick` | Кирпич | камень |
| 1 | `aerated_concrete` | Газобетон / пеноблок | блоки |
| 2 | `ceramic_block` | Керамический блок | блоки |
| 3 | `timber` | Брус / бревно | дерево |
| 4 | `frame` | Каркас (открытый) | дерево |
| 5 | `sip` | СИП-панели | дерево |
| 6 | `monolith` | Монолит | бетон |
| 7 | `hidden` | Скрыт отделкой | — |
| 8 | `unclear` | Не определить (далеко, тень, плёнка) | — |

**Группы** нужны для мягкого сравнения: газобетон вместо керамического блока — расхождение внутри группы (`low`), брус вместо газобетона — между группами (`high`).

### 5.3 Ключевая идея: материал «фиксируется» до отделки

После отделки фасада материал не виден: под сайдингом может быть что угодно. Поэтому:

- Материал определяется на облётах **стадии «Стены»**, пока кладка открыта.
- Уверенный результат **закрепляется за объектом** (`object.material_observed`) вместе со ссылками на снимки-доказательства.
- На поздних облётах `hidden` — это норма, а не ошибка: берётся закреплённое значение.
- Если стадия «Стены» пропущена (облётов не было, а на первом облёте уже отделка), материал = `unknown` с пометкой «не удалось подтвердить». Это повод для ручной проверки, а не тревога.

Отсюда практическое правило для **расписания облётов** (раздел 4.6): обязательный облёт в окне стадии «Стены».

### 5.4 Голосование по фасадам

1. Кропы с `hidden` и `unclear` не голосуют.
2. Голос кропа = уверенность классификатора × размер кропа (крупная открытая стена надёжнее угла на краю кадра).
3. Материал объекта = класс с максимальной суммой голосов.
4. Уверенность = доля голосов победителя. Если два материала примерно поровну (например, цоколь кирпичный, а стены газобетон), возвращаются оба с пометкой `mixed`.
5. Нужно **минимум 2 фасада** с открытой стеной, иначе `unclear`.

### 5.5 Сравнение с проектом и сигнал

Только если `project.wall_material` задан. Если нет — `match: "no_project"`, сигналов нет, материал идёт в оценку и акт.

| Факт против проекта | Сигнал | Уровень |
|---|---|---|
| совпал | — | — |
| другой материал в той же группе | `MATERIAL_DEVIATION` | 🟡 `yellow`, уточнить у клиента |
| другая группа, уверенность ≥ 0.8 на ≥ 2 фасадах | `MATERIAL_MISMATCH` | 🔴 `red`, ручная проверка: подозрение на нецелевое использование и переоценка залога |
| другая группа, уверенность ниже | — | пересъёмка в хорошем свете, тревоги нет |
| не удалось определить | `MATERIAL_UNVERIFIED` | 🟡 `yellow`, если стадия «Стены» уже пройдена |

Сигналы добавляются в общий список раздела 4.3 и участвуют в уровне риска наравне с остальными. Мера для `MATERIAL_MISMATCH` — `MANUAL_INSPECTION`, только после подтверждения сотрудником.

### 5.6 Выход агента

```json

  "agent": "material",
  "model": "yolo26m-cls@v1",

  "material_label": "Брус / бревно",
```

### 5.7 Данные и обучение

- Датасет кропов получается **из той же разметки**, что и в части 1: рамки `walls_*` уже есть, к ним добавляется только метка материала. Разметчик делает это за секунды на кроп.
- Цель: 150–300 кропов на класс. Кирпич и газобетон встречаются часто, СИП и монолит редко — для них аугментации и дозаполнение из открытых фото фасадов.
- `imgsz=384`, аугментации по цвету и яркости (снимки в разное время дня), **без** поворотов на 90° (у бруса и кладки важна ориентация).
- Деление train/val по объектам, как в части 1.
- Метрики: точность и confusion matrix по классам, **отдельно точность по группам** (для сигнала важна именно она).

### 5.8 Страховка: VLM как второе мнение

Пока данных мало, кроп стены можно параллельно отправлять в локальную VLM (например, Qwen-VL) с вопросом «из какого материала стена». Если YOLO-cls и VLM расходятся, `MATERIAL_MISMATCH` не поднимается автоматически, а уходит человеку. На демо это хорошо показывает «человека в контуре».

## 8. Мок-режим

Включается переменной `MOCK=1`. API отдаёт заготовленные данные из `mocks/` и не трогает модель. Поля объектов — в формате реестра банка, облёты и исходы звонков — демо. Моки покрывают ветки схемы банка (раздел 13) и сценарии раннего предупреждения (раздел 4) — это готовый сценарий демо:

| Объект | Реестр | Облёт и шаги | Риск | Путь дирижёра | Сценарий |
|---|---|---|---|---|---|
| obj_demo_1 | не в залоге, осталось 80% срока | облётов нет | 🟢 | вход 1 → SMS-напоминание | ранняя стадия, только напоминание |
| obj_demo_2 | не в залоге, осталось 50% срока, ПЗ нет | контрольный облёт: фундамент, 15% при плане 50% | 🟠 | ранний сигнал → вход 3: звонок о причине | **главный кейс демо:** схема банка до 30% срока молчит, мы звоним сейчас |
| obj_demo_3 | осталось 20% срока | облёт: дом готов | 🟢 | вход 1 → Стратегия 1 → вход 3 → Стратегия 7 | построен → оформить в залог |
| obj_demo_4 | осталось 20% срока | облёт: стены без кровли; звонок: не хватает денег по договору | 🟠 | вход 3 → Стратегия 3 | доп. финансирование на достройку |
| obj_demo_5 | срок истёк | облёт: стены; звонок не удался; клиент согласен на замену | 🟠 | вход 3 → 4 → Стратегия 4 | замена обеспечения |
| obj_demo_6 | осталось 25% срока | облёт: 75%, по плану; отступ от границы 1,8 м | 🟢 | вход 5 → прогноз «успеет» → Стратегия 5 | мониторинг без звонка хорошему клиенту; освоение: отступ на проверку |
| obj_demo_7 | осталось 10% срока, ПЗ есть | облёт: стены в процессе, 30%; звонок не удался | 🔴 | вход 3 → 4 → 5 «не успеет» → 6 → Стратегия 6 → вход 8 | суд → AI-оценка → торги |

| obj_demo_9 | — | облёт с низкой уверенностью | — | дирижёр ждёт | `data_status: reshoot`, тревоги нет, назначен повторный облёт |
| obj_demo_10 | проект: газобетон | стены по плану, **брус** | 🔴 | ручная проверка | часть 2: строят по плану, но не то → ручная проверка |

Загрузка облёта в мок-режиме тоже работает: через 3 секунды статус меняется на `done` и возвращается заготовленный результат. Импорт реестра в мок-режиме работает по-настоящему: объекты создаются, а облёты у них появляются только после загрузки. **Фронт разрабатывается против мока с первого дня, ML обучается параллельно.**

`GET /meta` отдаёт `"mock": true`, а фронт показывает плашку «Демо-данные».

## 9. Нефункциональное

- **Неизменяемость.** Оригиналы снимков не изменяются, при загрузке считается sha256. Правки, исходы шагов и решения только добавляются, ничего не удаляется.
- **CORS** открыт для адреса dev-сервера фронта (переменная `CORS_ORIGINS`).
- **Конфиг** через переменные окружения: `DB_URL`, `STORAGE_DIR`, `WEIGHTS_PATH`, `MOCK`, `CORS_ORIGINS`, `GIGACHAT_*` (см. [GIGACHAT.md](GIGACHAT.md)).
- **Авторизация** на хакатоне не нужна: автор ревью и шагов передаётся заголовком `X-User` (по умолчанию `demo`).
- **Скорость:** один облёт (6 снимков) обрабатывается до минуты на CPU. Если не укладываемся — экспорт модели в ONNX или OpenVINO.
- **ИБ и 152-ФЗ.** Ответ банка: на хакатоне внешние облачные модели можно, в целевом процессе всё хранится во внутреннем контуре. Поэтому:
  - снимки и модели детекции работают только локально, в облако снимки не уходят;
  - GigaChat на хакатоне анализирует факты и предлагает стратегию, объяснение и тексты (раздел 13.8). В него уходят обезличенные результаты агентов, план и факт, прогноз, ПЗ и исходы шагов; без ФИО, адреса, кадастрового номера и номера кредита. Свободные комментарии перед отправкой очищаются от этих данных;
  - в пилоте GigaChat заменяется моделью во внутреннем контуре без правок логики: клиент LLM за интерфейсом.

## 13. AI-дирижёр: стратегии работы с клиентом

Дирижёр использует GigaChat для анализа результатов YOLO и других агентов вместе с данными реестра, планом строительства, прогнозом и исходами коммуникаций. GigaChat предлагает одну из 8 стратегий либо следующий шаг для получения недостающих данных и объясняет предложение на основе переданных фактов.

Схема банка задаёт ограничения допустимости. Бэкенд рассчитывает сроки, готовность, прогноз и риск, формирует доступные стратегии и шаги, проверяет предложение GigaChat и сохраняет подтверждённый путь по схеме. Подтверждение сотрудником определяется разделом 13.6. Дерево ниже также служит резервным алгоритмом при недоступности LLM или отклонении её ответа.

### 13.1 Входы

| Данные | Откуда |
|---|---|
| залог, регистрация ОН, ПЗ, сроки | реестр (раздел 4.1) |
| построен / не построен | агент готовности: `bank_readiness = 100` (раздел 3.4) или фактическая дата в реестре |
| прогноз завершения в срок | раздел 4.8 |
| уровень риска и сигналы | раздел 4 |
| исходы коммуникаций и проверок | сотрудник в карточке (`POST /objects/{id}/steps`) |
| оценка ОН | раздел 15 |

### 13.2 Узлы

| Узел | Вопрос | Ответы | Кто отвечает |
|---|---|---|---|
| `PLEDGED` | ОН оформлен в залог? | да / нет | реестр |
| `TERM` | Где объект по сроку? | осталось > 70% / 30–70% / ≤ 30% / истёк | даты реестра |
| `BUILT` | ОН построен? | да / нет | облёт или реестр |
| `COMM_REASON` | Коммуникация: почему не достроен | неполное финансирование / трудная жизненная ситуация / другое / неуспешна | сотрудник |
| `CHECK_UNDERFUNDED` | Неполное финансирование по договору? | да / нет | сотрудник по договору |
| `CHECK_HARDSHIP` | Трудная жизненная ситуация? | да / нет | сотрудник |
| `FORECAST` | Построит в срок? | да / нет | прогноз (раздел 4.8) |
| `OVERDUE` | Есть ПЗ? | да / нет | реестр, позже АБС |
| `COMM_SETTLEMENT` | Предложение инструментов урегулирования | согласен / не согласен | сотрудник |
| `COMM_COLLATERAL` | Коммуникация: замена обеспечения | согласен / не согласен | сотрудник |
| `COMM_PLEDGE` | Коммуникация: оформить ОН в залог | согласен / не согласен | сотрудник |

### 13.3 Дерево

Номера входов совпадают с номерами линий на схеме банка. Дерево задаёт проверяемые условия переходов и резервное поведение; GigaChat получает эти правила и доступные на текущем шаге варианты. Неизвестный исход коммуникации остаётся неизвестным до ввода сотрудником.

```
Вход 1 — объект не в залоге
  TERM:
    осталось > 70%          → SMS/PUSH: напоминание о плановой дате → ждём
    осталось 30–70%         → в схеме нет: контрольный облёт при 50% срока (вопрос 12.1)
    осталось ≤ 30% / истёк  → полётное задание + SMS об осмотре → СТРАТЕГИЯ 1 «Вылет дрона»
                              → результат облёта → вход 3 или 5 (13.4)

Вход 2 — объект в залоге
  OVERDUE:
    нет → назад к дирижёру, ждём следующего события
    да  → COMM_SETTLEMENT:
            согласен    → CHECK_HARDSHIP: да → СТРАТЕГИЯ 2 «Реструктуризация»
                                          нет → СТРАТЕГИЯ 6 «Передача в суд»
            не согласен → в схеме нет: ручное решение (вопрос 12.3)

Вход 3 — облёт показал, что надо говорить с клиентом
  BUILT:
    да  → COMM_PLEDGE → СТРАТЕГИЯ 7 «Регистрация ОН и оформление в залог»
    нет → COMM_REASON:
            неполное финансирование    → CHECK_UNDERFUNDED: да  → СТРАТЕГИЯ 3 «Доп. финансирование на достройку»
                                                            нет → в схеме нет: ручное решение (12.3)
            трудная жизненная ситуация → CHECK_HARDSHIP: да  → СТРАТЕГИЯ 2
                                                         нет → СТРАТЕГИЯ 6
            другое                     → в схеме нет: ручное решение (12.3)
            неуспешна                  → вход 4

Вход 4
  TERM:
    истёк    → COMM_COLLATERAL: согласен    → СТРАТЕГИЯ 4 «Замена обеспечения»
                                не согласен → вход 2
    не истёк → вход 5

Вход 5
  FORECAST:
    построит    → SMS/PUSH: напоминание о плановой дате → СТРАТЕГИЯ 5 «Мониторинг»
    не построит → вход 6

Вход 6
  OVERDUE:
    да  → СТРАТЕГИЯ 6 «Передача в суд» → вход 8
    нет → COMM_COLLATERAL (как во входе 4)

Вход 8
  VALUATION: AI-оценка ОН (раздел 15)
    → LISTING: размещение ОН на PortalDA, Авито
    → AUCTION: торги
    → СТРАТЕГИЯ 8 «Реализация ОН»
```

После любой стратегии данные возвращаются дирижёру, и цикл продолжается со следующего события: импорт реестра, облёт, исход шага, ежедневный пересчёт.

### 13.4 Точки входа

Схема банка выходит из дирижёра восемью линиями, но не говорит, когда какая. Наша трактовка (вопрос 12.2):

| Событие | Вход |
|---|---|
| импорт реестра или ежедневный пересчёт, объект не в залоге | 1 |
| то же, объект в залоге | 2 |
| результат облёта: построен | 3 |
| результат облёта: не построен, и срок истёк или риск 🟠 / 🔴 | 3 |
| результат облёта: не построен, срок не истёк, риск 🟢 / 🟡 | 5 — без звонка клиенту, у которого всё по плану |
| Стратегия 6 подтверждена | 8 |

Вход 4 и вход 6 достигаются только внутри дерева.

### 13.5 Ранний сигнал внутри схемы

Схема банка реагирует на сроки: пока до плановой даты больше 30% срока, клиенту уходят только напоминания. Раннее предупреждение (раздел 4) работает поверх:

- 🟡 → внеплановый облёт (`FLIGHT_TASK`, Стратегия 1), даже если по сроку рано;
- 🟠 → вход 3 сразу: узнать причину, не дожидаясь последних 30% срока;
- 🔴 → ручная проверка (`MANUAL_INSPECTION`), после подтверждения — вход 3.

Так ветка «узнать причину» запускается на месяцы раньше, пока клиент ещё платит.

### 13.6 Шаги и подтверждение

| Шаг / стратегия | Кто выполняет | Нужно подтверждение сотрудника |
|---|---|---|
| `SMS_TERM_REMINDER`, `FLIGHT_TASK` (с SMS об осмотре) | авто | нет |
| `COMM_*`, `CHECK_*` | сотрудник вносит исход | — |
| `MANUAL_INSPECTION`, `LISTING`, `AUCTION` | сотрудник | — |
| `VALUATION` | авто | да, перед размещением |
| Стратегии 1, 5 | авто | нет |
| Стратегии 2, 3, 4, 6, 7, 8 | дирижёр предлагает | да |

Пока шаг ждёт человека, объект висит в очереди задач (`GET /tasks`). Исход, которого дирижёр не ждёт, отклоняется (`STEP_NOT_EXPECTED`).

`recommendation` содержит предложение GigaChat после разбора JSON. `llm_status: accepted` означает успешную проверку бэкендом; стратегия при этом ещё может ждать сотрудника (`strategy.state: proposed`). Допустимые значения новых полей и ссылки `evidence_refs` определены в [API.md](API.md), контракт `GET /objects/{object_id}/conductor`.

`path` строится бэкендом по проверенным фактам. Кроме узлов из 13.2 в него попадают выполненные шаги и стратегии (`FLIGHT` — облёт по Стратегии 1), чтобы путь читался целиком. Текст GigaChat не создаёт исходы шагов и не меняет факты реестра или агентов.

`strategy.state`: `waiting` (ждём исход шага), `proposed` (ждёт подтверждения), `confirmed`, `rejected`, `done`.

### 13.8 Анализ и рекомендации через GigaChat

Основной режим: **YOLO → структурированные факты → GigaChat → проверка бэкендом → предложение сотруднику или разрешённый автоматический шаг**. Обучать GigaChat для первой версии не требуется: готовой модели через API передаются правила процесса и факты объекта. Подключение и формат запроса — в [GIGACHAT.md](GIGACHAT.md), раздел 9.

**Контекст запроса:** готовность и уверенность агентов, дата облёта, материал и освоение участка, плановые этапы с датами (когда график появится), рассчитанное отставание и прогноз, ПЗ, залог, регистрация, подтверждённые исходы шагов. Для каждого факта передаётся ссылка на источник в снимке контекста: например, `readiness.bank_readiness`, `term.expired`, `steps.st_44.outcome`. Если графика этапов нет, явно указывается используемый линейный план из раздела 4.2. Отсутствующие значения передаются как `null`, а не как отрицательные ответы.

**Результат GigaChat:** JSON с полями `strategy_code`, `next_step_code`, `reason`, `evidence_refs`, `missing_data` по контракту API. Модель выбирает из переданных допустимых кодов. Если условий для стратегии пока нет, `strategy_code = null`, а следующий шаг нужен для получения данных или проверки. Например, отставание при отсутствии ПЗ может вести к выяснению причины через `COMM_REASON` до появления задолженности.

**Бэкенд проверяет:**
- JSON по Pydantic-схеме, коды по справочникам, выбранные стратегию и шаг по допустимым вариантам;
- существование ссылок `evidence_refs` и соответствие объяснения исходным фактам; текст модели не считается новым доказательством;
- все условия схемы банка, качество снимков и необходимые исходы коммуникаций; неизвестные исходы GigaChat заполнять не может;
- актуальность снимка контекста перед применением ответа и обязательность подтверждения по разделу 13.6.

Непроверяемое или противоречащее фактам объяснение отклоняется либо передаётся сотруднику на проверку. Рекомендация не изменяет готовность, даты, прогноз или риск, рассчитанные бэкендом. Стратегии 2, 3, 4, 6, 7, 8 остаются в `proposed` до подтверждения сотрудником; GigaChat не исполняет финансовые и судебные действия.

**Асинхронность и резерв:** при новом событии бэкенд сразу рассчитывает допустимый шаг по дереву банка и возвращает `decision_source: rules_fallback`, `llm_status: pending`, `recommendation: null`. Запрос GigaChat выполняется в воркере. Проверенный ответ создаёт новую запись решения с `decision_source: gigachat`, `llm_status: accepted`. Уже выполненный шаг повторно не запускается, подтверждённая стратегия без нового решения сотрудника не заменяется. Устаревший ответ не применяется к новому состоянию объекта.

При тайм-ауте, ошибке API или отсутствии ключа используются `decision_source: rules_fallback`, `llm_status: unavailable`. При некорректной схеме или нарушении ограничений — `rules_fallback` и `llm_status: rejected`. Действуют те же условия подтверждения сотрудником. Автоматические сигналы раннего предупреждения рассчитываются независимо от доступности GigaChat. В `MOCK=1` сетевых вызовов LLM нет: рекомендации берутся из фикстур и проходят ту же проверку.

Для аудита сохраняются снимок контекста, исходный ответ модели, результат проверки, идентификатор модели, версия промпта и время запроса. В API и интерфейс как предложение попадает только проверенная рекомендация; непроверенный ответ остаётся в журнале аудита. Также GigaChat готовит объяснения, черновики SMS и сценариев звонков, краткую сводку по журналу шагов. Для текстов остаются шаблоны из `configs/conductor.yaml`.

### 13.9 Конфиг

`configs/conductor.yaml`: пороги срока (70% / 30%), контрольная точка в середине срока, точки входа (13.4), условия допустимости стратегий, версия промпта, тайм-аут LLM и шаблоны текстов. Ключи доступа — только в переменных окружения `GIGACHAT_*`. Пороги банка меняются без релиза (`PUT /config/conductor`).

## 14. Освоение участка

### 14.1 Что проверяем

По ответу банка:
- **посадка дома по кадастру:** дом стоит внутри своего участка;
- **отступ от границ:** от дома до границы участка не меньше нормы (`min_setback_m`, по умолчанию 3 м, уточняется по правилам землепользования муниципалитета);
- **ВРИ:** вид разрешённого использования участка допускает жилой дом;
- **благоустройство** — опционально и только наличие: забор, хозпостройки, дорожки и площадки. Процент не считаем.

### 14.2 Как

1. На `top_high` детектор находит `building`, `outbuilding`, `fence`, `paving` (раздел 3.2).
2. Снимок привязывается к земле: GPS, относительная высота, фокусное расстояние, размер матрицы и азимут из EXIF/XMP дают метры на пиксель и поворот. Камера должна смотреть вниз (наклон гимбала около −90°), иначе `status: unverified`.
3. Границы участка из кадастра переводятся в ту же систему в метрах. Считаются: внутри ли дом, минимальное расстояние от дома до границы и с какой стороны.
4. ВРИ берётся из кадастровых сведений по номеру участка, не со снимка. Список допустимых — в `configs/land.yaml`: 2.1 (ИЖС), 2.2 (ЛПХ, приусадебный участок), 13.2 (садоводство). В реестре есть участки в СНТ и ДНТ, поэтому садоводство в списке.

### 14.3 Точность и ограничения

- На хакатоне дом — рамка детектора. У повёрнутого дома рамка больше контура, и отступ получается меньше настоящего. Поэтому нарушение — задача на проверку, а не тревога. В пилоте — маска сегментации (YOLO26-seg).
- GPS дрона без RTK ошибается на метры, а это сравнимо с нормой отступа. В требования к полётному заданию подрядчика — RTK или PPK. Без них сдвиг можно поправить по линии забора, если он виден.
- Снимки только с GPS к земле не привязать: `status: unverified`, проверка — сотрудником по снимку.

### 14.4 Сигналы

| Код | Условие | Что происходит |
|---|---|---|
| `OUT_OF_BOUNDS` | дом выходит за границу участка | задача на проверку, в акт |
| `SETBACK_SUSPECT` | отступ меньше нормы | задача на проверку, в акт |
| `VRI_MISMATCH` | ВРИ не допускает жилой дом | задача на проверку документов |

В уровень риска эти сигналы не входят (раздел 4.3). Они показываются в блоке «Освоение участка» карточки и попадают в акт осмотра.

## 15. Оценка стоимости ОН

### 15.1 Зачем

- **Стратегия 8:** ориентир для начальной цены при размещении на PortalDA, Авито и на торгах.
- **Переоценка залога:** банк по осмотру определяет стоимость и при необходимости переоценивает (Кейс 3, п. 1).

### 15.2 Расчёт на хакатоне

```
площадь         = площадь застройки × этажность
стоимость_дома  = площадь × удельная_стоимость(материал) × readiness_pct / 100
стоимость_ОН    = стоимость_дома + стоимость_участка
```

| Вход | Откуда | Если нет |
|---|---|---|
| площадь застройки | проект | `building` с `top_high` (раздел 14), пометка «по снимку» |
| этажность | проект | 1, пометка «не подтверждено» |
| материал | агент материала, закреплённый за объектом (раздел 5.3) | средняя удельная стоимость, пометка |
| готовность | агент готовности или правка человека | — |
| удельные стоимости, вилка ±% | `configs/valuation.yaml` | — |
| стоимость участка | кадастровая стоимость или ввод сотрудником | без участка, пометка |

Удельные стоимости в конфиге — **заглушки**, нужны данные банка (вопрос 12.5). Результат — ориентир с вилкой и разложением расчёта, а не отчёт оценщика. Перед размещением его подтверждает сотрудник.

### 15.3 Переоценка

Если у объекта указана залоговая стоимость и новая оценка отличается от неё больше порога (`revaluation_threshold`, заглушка 20%), появляется сигнал `REVALUATION_NEEDED` и задача на проверку.

### 15.4 Пилот

Сравнительный подход: объявления о продаже похожих домов рядом. Удельные стоимости — по методике банка.

### 15.5 Выход

```json
{
  "agent": "valuation",
  "rules": "valuation@v1",
  "value_rub": 4300000,
  "range_rub": [3700000, 4900000],
  "breakdown": {
    "footprint_m2": 96, "footprint_source": "project",
    "floors": 2, "floors_source": "project",
    "material": "aerated_concrete", "unit_cost_rub_m2": 38000,
```

## 16. Акт осмотра

Банк по итогам осмотра составляет акт по форме Приложения 1 к кейсу и загружает его в АС «Калита». Система заполняет акт из облёта: то, что видно с дрона, — автоматически, остальное — сотрудник. У каждого поля указан источник.

| Поле акта | Чем заполняется |
|---|---|
| Номер и дата кредитного договора | объект |
| Дата и время осмотра | дата облёта из EXIF или загрузки |
| Адрес объекта | реестр |
| Тип объекта | «жилой дом (ИЖС)», стадия по шкале банка |
| Площадь | проект или `building` с `top_high`, с пометкой «по снимку» |
| Количество комнат | с дрона не определяется — сотрудник |
| Материал наружных стен | агент материала (раздел 5) |
| Материал перегородок | с дрона не определяется — сотрудник |
| Этажность | проект — иначе сотрудник |
| Год постройки | фактическая дата из реестра или «строится» |
| Принадлежность, перепланировка, вид права на участок | документы — сотрудник |
| При осмотре установлено (дефекты) | шаблоном из элементов: нет кровли, пустые проёмы без окон, нет входной двери, откат (`REGRESS`), нарушения из раздела 14 |
| Состояние: удовлетворительное / неудовлетворительное | предлагается правилом из конфига, выбирает сотрудник |
| Осмотр проводил | сотрудник, подтвердивший облёт; приписка «с применением БПЛА, облёт fl_…, sha256 снимков» |

К акту прикладываются 6 снимков облёта с рамками. Отдаётся как JSON и как HTML для печати (`GET /flights/{flight_id}/act`). Интеграция с «Калитой» — в пилоте.
