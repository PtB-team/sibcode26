# Подключение моделей и выбор нужного объекта

## Как работает обработка

```text
Исходное фото
  → детектор YOLO, imgsz=1280
  → рамки стен и остальных элементов
  → исключение рамок за пределами заданной области объекта, если область передана
  → вырезка каждой подходящей стены с полем 10% с каждой стороны
  → классификатор материала, imgsz=384
  → объединение наблюдений по фасадам
  → факты для расчётов и GigaChat
```

Детектор вызывается один раз на снимок. Его результат используется и для готовности, и для поиска стен. Классификатор получает вырезку из исходного снимка после учёта EXIF-ориентации, а не из превью. Поле ограничивается краями изображения.

Классификатор обрабатывает только `walls_partial` и `walls_full`. Верхние ракурсы для материала исключаются. `hidden` и `unclear` сохраняются как наблюдения, но в голосовании за материал не участвуют. Материал читается из имён классов весов; числовые индексы из `configs/materials.yaml` для декодирования весов не используются. СИП и монолит есть в справочнике сервиса, но в текущей разметке ML для них нет примеров; сервис не добавляет отсутствующие классы в модель.

При уверенном материале на ненадёжно найденной стене наблюдение не получает голос: проверяются обе уверенности. Если видимый кирпич совпадает с найденной отделкой фасада, ставится `CLADDING_MAY_HIDE_STRUCTURE` и требуется проверка несущего материала. Ответ модели сохраняется.

## Веса и запуск

После окончания обучения получите у ML два локальных файла:

- `weights/readiness_yolo26m.pt` — детектор, 13 классов, включая `fence` с номером 12;
- `weights/material_yolo26m-cls.pt` — классификатор материала стен.

Установите зависимости инференса, если их ещё нет:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-inference.txt
```

Версию Ultralytics согласуйте с ML-командой при передаче весов: окружение должно поддерживать использованную архитектуру YOLO26.

В существующем `.env` задайте эти параметры, сохранив остальные настройки и ключи:

```dotenv
MOCK=0
DETECTOR_FACTORY=agents.readiness.yolo:create_detector
READINESS_WEIGHTS=weights/readiness_yolo26m.pt
MATERIAL_MODEL_FACTORY=agents.material.yolo:create_predictor
MATERIAL_WEIGHTS=weights/material_yolo26m-cls.pt
```

Перезапустите API и воркер по [INTEGRATION.md](INTEGRATION.md). При отсутствии файла или ошибке модели сервис показывает недоступность, а не выдуманный результат. Классификатор материала зависит от детектора стен: при его недоступности появляется `module_errors.material.code=DETECTOR_REQUIRED`. Готовность продолжает работать при недоступном классификаторе. Старые адаптеры с `predict(image, image_id)` поддерживаются.

Факт загрузки настоящих весов и качество распознавания нужно проверить после передачи файлов. Тесты интеграции используют подставные модели и проверяют обработку результатов, не точность YOLO.

## Формат материала

Запись стены в `last_flight.material_result.per_view` содержит согласованные с ML поля:

```json
{
  "image_id": "img_301",
  "cls": "walls_full",
  "conf": 0.91,
  "bbox": [0.08, 0.10, 0.62, 0.71],
  "material": "brick",
  "material_conf": 0.84
}
```

`bbox` — исходная рамка стены в долях ориентированного кадра `[x1,y1,x2,y2]`. `conf` — уверенность детектора; `material_conf` — классификатора. Дополнительно передаются `detector_confidence`, `confidence` (уверенность материала), `crop_bbox` (рамка с полем), `visibility`, ракурс, ссылка на кроп, причины исключения и проверки. Совместимое поле `class` по-прежнему обозначает **материал**. Если старая модель не возвращает уверенность детектора, `conf` остаётся совместимым с прежней уверенностью материала.

Кровля, окна и остальные классы находятся в детекциях снимка и не передаются в классификатор материала. Забор загружается и сохраняется как детекция, но сам по себе сейчас не увеличивает процент готовности дома.

## Как исключаются соседи

Поддерживается необязательная область `target_bbox` в `meta` каждого загружаемого снимка:

```json
[
  {"target_bbox": [0.08, 0.10, 0.62, 0.95]},
  {"gps": [55.1, 83.2], "target_bbox": [0.15, 0.05, 0.80, 0.90]}
]
```

Рамка относится к нужному зданию либо области нужной стройки на конкретном кадре. Детекция учитывается, только если не меньше 90% её площади находится внутри области. Исключённые детекции сохраняются в ответе снимка с `target_included=false`, `target_exclusion_reason=OUTSIDE_TARGET` и `counted=false`. В классификатор они не передаются. Для старых материальных адаптеров их наблюдения также фильтруются перед голосованием.

Область передаёт вызывающая сторона; бэкенд сохраняет автора `X-User` и время. Она **не доказывает кадастровую принадлежность**. Самостоятельное определение этой области по кадастровому номеру пока не подключено. При отсутствии области фильтрации по зданию нет: сохраняются прежнее поведение и необходимость подтверждения `target_confirmed`. В `/meta` явно указано `target_region_filter=true`, `automatic_target_identification=false`. Это подготовленный фильтр, а не готовая автоматическая геопривязка. Новый ручной интерфейс выбора области не добавлялся.

## Автоматический выбор по кадастровому номеру

Для него нужен дополнительный источник данных:

1. По кадастровому номеру получить проверенный контур нужного участка. Если указан номер здания, сначала установить связанный земельный участок. Адрес или сам номер без координат контур не заменяет.
2. Привязать снимок к местности, затем сопоставить найденные здания и элементы с контуром участка. Для фасадов нужно учитывать перспективу и высоту здания; область на снимке сверху нельзя переносить на другой ракурс без преобразования.
3. Автоматически выбирать объект при однозначном соответствии с учётом погрешности. Неоднозначность, отсутствующие границы или недостаток метаданных должны давать состояние «требуется проверка», а не произвольный выбор центрального дома.

В доступных 72 снимках DJI M3M найдены GPS, высота, ориентация камеры и параметры калибровки. Бэкенд сохраняет эти параметры для последующей геопривязки. Наличие тегов само по себе не подтверждает её точность: относительная высота не обязательно равна высоте над землёй в точке объекта, а наличие RTK-тегов не означает фиксированное решение. Нужны проверка системы высот, калибровки, рельефа и согласованности координат.

Сейчас у команды есть номера и фото. Источник кадастровых контуров и автоматическая проекция ещё не подключены. Существующая GPS-проверка сопоставляет положение камеры с участком; она не определяет, какому зданию принадлежат все рамки на фотографии.
