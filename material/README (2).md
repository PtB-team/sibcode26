## 0. Зачем это всё

**Главная задача — превентивно реагировать на финансовые трудности клиента и автоматически выбирать стратегию работы с ним.**

Банк выдал кредит на дом со сроком строительства 2 года. Прошёл год: по плану должна стоять половина дома, а дрон видит один фундамент. Платежи пока идут вовремя, но это уже звоночек: деньги, скорее всего, кончились или ушли не туда, и просрочка появится через несколько месяцев. По схеме банка, пока до плановой даты больше 30% срока, клиенту уходят только напоминания. Мы замечаем отставание сейчас и запускаем ветку «узнать причину» на месяцы раньше, пока можно мягко договориться: доп. финансирование, реструктуризация, замена обеспечения.

Отсюда цепочка:

```
снимки → агенты: стадия и %, материал, освоение участка
       → план против факта и прогноз → сигнал риска
       → GigaChat: анализ фактов и предложение стратегии → проверка бэкендом → стратегия и следующий шаг
```

Стадия и % — это **вход**, а продукт — **сигнал отставания и выбранная стратегия**. Ошибка модели здесь стоит дорого: ложная тревога означает лишний звонок хорошему клиенту, пропуск — потерянное время. Поэтому тревога поднимается только по уверенному результату, а неуверенный сначала уходит на пересъёмку.

Что ждёт банк (тизер кейса) и где это у нас:
- **степень готовности** — агент готовности (раздел 3), наружу в шкале банка 0 / 50 / 100;
- **материал стен** — агент материала (раздел 5);
- **освоение земельного участка** — посадка дома по кадастру, отступы, ВРИ (раздел 14);
- **AI-дирижёр** со стратегиями по задолженности, стадии и прогнозу сроков — схема банка с 8 стратегиями (раздел 13), прогноз (раздел 4.8), оценка ОН для реализации (раздел 15).

Плюс то, что добавляем от себя:
- **раннее предупреждение** (раздел 4): план против факта, сигналы, уровни риска — запускает ветки дирижёра раньше срока;
- **акт осмотра** (раздел 16): форма банка, заполненная из облёта;
- **API** (раздел 6) и **фронт** (раздел 7);
- **критерии хакатона** (раздел 11): код, новизна, презентация.

## 1. Что делаем

```
Реестр банка (xlsx) → импорт: сроки, ПЗ, залог, регистрация
        │
        ▼
Дирижёр по сроку: напоминание / полётное задание
        │
        ▼
Оператор загружает облёт (4 фасада + низкий и высокий надир)
        │
        ▼
API сохраняет снимки (sha256, EXIF) → ставит задачу в очередь
        │
        ▼
Воркер: YOLO находит элементы стройки → агрегация по ракурсам → правила
        ├─ кропы стен → классификатор материала → голосование по фасадам
        └─ высокий надир → посадка дома, отступы от границ, забор, постройки
        │
        ▼
Результат: стадия, % и шкала банка, уверенность, объяснение, рамки на фото
        │
        ▼
Раннее предупреждение: факт против плана + ПЗ → уровень риска, сигналы, прогноз
        │
        ▼
AI-дирижёр: GigaChat анализирует факты → предлагает шаг или стратегию 1–8
        │
        ▼
Бэкенд проверяет рекомендацию по схеме банка → подтверждение сотрудника, если требуется
        │
        ▼
Веб-морда: лента тревог и задач → карточка → итог звонка → «Подтвердить стратегию» → акт осмотра
```

Главный принцип: **YOLO оценивает снимки, бэкенд рассчитывает готовность, отставание и риск, GigaChat анализирует факты и предлагает стратегию с объяснением.** В GigaChat передаются результаты агентов, план и факт, прогноз, ПЗ и подтверждённые исходы коммуникаций. Бэкенд проверяет рекомендацию по схеме банка и сохраняет доказательства; требующие подтверждения стратегии принимает сотрудник. При недоступности GigaChat работают правила банка (раздел 13.8).

## 2. Стек и структура

| Слой | Хакатон | Пилот |
|---|---|---|
| Язык | Python 3.11+ | Python 3.11+ |
| API | FastAPI + Pydantic | FastAPI + Pydantic |
| БД | SQLite | PostgreSQL |
| Снимки | локальная папка | MinIO / S3 |
| Очередь | отдельный процесс-воркер, задачи в таблице БД | RQ / Celery + Redis |
| ML | Ultralytics YOLO26m-det (запасной вариант YOLO11m) | то же, экспорт в ONNX / OpenVINO; для освоения — YOLO26-seg |
| LLM | GigaChat API: анализ фактов, рекомендация стратегии, объяснения и тексты | модель во внутреннем контуре банка |
| Фронт | React / Vue, стек фронтендера | то же |

```
repo/
├── api/            # FastAPI: роуты, схемы, CORS, мок-режим, импорт реестра
├── worker/         # процесс инференса: берёт задачи, пишет результат
├── agents/
│   ├── readiness/  # детектор + агрегация + правила → JSON
│   ├── material/   # кропы стен + классификатор + голосование
│   ├── land/       # освоение участка: привязка top_high, отступы, ВРИ
│   ├── early_warning/  # план против факта, прогноз, сигналы, уровень риска
│   ├── conductor/  # AI-дирижёр: GigaChat, проверка рекомендаций, дерево банка как резерв
│   ├── valuation/  # оценка стоимости ОН
│   └── act/        # акт осмотра
├── schemas/        # общие Pydantic-модели (контракт API и агентов)
├── configs/
│   ├── classes.yaml    # классы детектора, русские названия, цвета, маска ракурсов
│   ├── stages.yaml     # веса этапов, пороги, шкала банка
│   ├── materials.yaml  # классы материала, группы, пороги сравнения
│   ├── risk.yaml       # пороги отставания, уровни риска, сезонная пауза
│   ├── conductor.yaml  # пороги срока, точки входа, шаблоны текстов
│   ├── land.yaml       # норма отступа, допустимые ВРИ
│   └── valuation.yaml  # удельные стоимости, вилка, порог переоценки
├── mocks/          # демо-объекты, снимки, контуры участков для мок-режима
├── data/           # датасет и разметка (не в git)
└── weights/        # веса модели (не в git)
```

Правила работы:
- Модель загружается **один раз** при старте воркера.
- Инференс **никогда не идёт внутри HTTP-запроса**.
- Контракт данных описан один раз в `schemas/`, а API и воркер его импортируют.
- GigaChat предлагает стратегию по структурированным фактам; бэкенд проверяет допустимость, сотрудник подтверждает действия согласно разделу 13.6. Вызовы LLM выполняются в воркере (раздел 13.8).

### 11.1 Качество кода

- [ ] Импорт `Реестр_для_теста.xlsx` проходит без ошибок, есть тест на него.
- [ ] Все пороги и веса в `configs/*.yaml`, в коде нет магических чисел.
- [ ] Модель за интерфейсом (`Detector`, `MaterialClassifier`), LLM за интерфейсами (`StrategyAdvisor`, `TextWriter`): правила и проверка рекомендаций тестируются на фейковых детекциях и ответах LLM, модель меняется без правок логики.
- [ ] Логи в JSON, понятные коды ошибок (раздел 6.4).
- [ ] Ноутбуки обучения и отчёт о метриках в `ml/`, веса — по ссылке, не в git.
- [ ] Осмысленная история коммитов, без «fix», «fix2», «final_final».

### 11.2 Новизна

Не продаём «YOLO нашёл стены» — этим никого не удивить. Новое в другом:

1. **Сигнал раньше просрочки.** Сравнение плана с фактом ловит трудности клиента за месяцы до того, как появится ПЗ. Схема банка до последних 30% срока только напоминает — мы звоним раньше. **Это главный тезис.**
2. **GigaChat анализирует факты и предлагает стратегию по схеме банка.** Выбор ограничен 8 стратегиями и допустимыми шагами; бэкенд проверяет рекомендацию и её доказательства, сотрудник подтверждает действия по разделу 13.6.
3. **Две оси сравнения:** «когда» (срок и график) и «что» (материал). Первая ловит финансовые трудности, вторая — нецелевое использование и переоценку залога.
4. **Объяснимость через элементы.** Модель ищет элементы, стадию считают прозрачные правила, у каждого вывода есть рамка на фото и сработавшее правило. Банку и регулятору это важнее точности.
5. **Съёмка с ролями ракурсов:** 6 снимков, маска «класс × ракурс», noisy-OR по фасадам, проверка участка и отступов по высокому надиру.
6. **Материал «фиксируется» до отделки:** облёт планируется в окно стадии «Стены», и материал закрепляется за объектом.
7. **Защита от ложной тревоги:** неуверенный результат или не тот участок ведут к пересъёмке, а не к звонку клиенту. Клиенту, у которого всё по плану, не звоним. Для красных сигналов и стратегий с деньгами клиента обязателен человек.
8. **Замкнутый контур:** правки сотрудников становятся разметкой для дообучения, отклонённые тревоги — материалом для подстройки порогов, акт осмотра заполняется сам.

## 12. Вопросы заказчику

Только те, ответ на которые меняет то, что мы делаем.

1. **Зона 30–70% срока.** В схеме дирижёра есть ветки «до даты больше 70% срока» и «осталось 30%», а между ними ничего нет. В реестре так сейчас 11 объектов из 34. Мы ставим контрольный облёт при 50% срока. Подходит?
2. **Точки входа дирижёра.** Из дирижёра выходят 8 линий, но не сказано, когда какая. Мы: после облёта «не построен, но по плану» идём сразу в прогноз (ветка 5) без звонка клиенту, в остальных случаях — в звонок о причине (ветка 3). Так можно?
3. **Ветки без продолжения.** «Неполное финансирование — нет», «Предложение инструментов урегулирования — не согласен», причина задержки не из двух вариантов схемы. Сейчас у нас это ручное решение сотрудника. Есть правило?
